# 지금 만든 흐름을 이해하기

이 프로젝트는 연구자가 작업을 제출하기 전에 실행 조건을 확인하고,
실행 후에는 실제 결과를 근거로 다음 자원을 추천하는 독립 서비스다.
기존 KubeEdge 실행 시스템은 그대로 둔다.

1. **장비와 실행 프로그램 등록**: 운영자가 어떤 장비에서 어떤 프로그램을
   검증했는지 등록한다. GPU나 NPU가 검색된 것만으로 모델 실행 가능이라고
   표시하지 않는다. 검증 기록이 있어야 실행 후보가 된다.
2. **작업 조건 등록**: 모델·데이터·입력 크기·정밀도·반복 수·품질 기준을
   고정한다. CPU 수나 메모리를 바꾸려면 변경 가능한 항목으로 미리 정한다.
3. **작업 제출**: API가 프로젝트 권한과 조건을 검사하고 DB에 먼저 기록한다.
   같은 요청을 두 번 보내도 같은 작업을 돌려준다.
4. **실제 실행 요청**: Kubernetes 경로는 대기 상태 Job을 만든다. Kueue가
   승인한 다음 스케줄러가 배치한다. Slurm 경로는 별도로 `sbatch`를 사용한다.
5. **결과 검증**: 프로그램 종료만 확인하지 않는다. 올바른 작업·장비 조건에서
   나온 결과인지, 필요한 계산량을 끝냈는지, 품질을 만족하는지 검사한다.
6. **자원 추천**: 같은 조건에서 얻은 독립 실행 결과가 충분히 쌓였을 때만
   추천한다. 측정이 부족하면 `NEEDS_PROFILE`이라고 답한다. 속도 차이가
   불확실하면 기준 구성을 유지한다.
7. **변경 승인**: 추천은 자동 실행 명령이 아니다. 사용자가 해당 추천 버전과
   후보를 승인한 뒤에 다른 구성으로 제출할 수 있다.

두 종류의 서명을 쓰는 이유는 다음과 같다. **작업 서명**은 “같은 실험인가”를,
**실행 환경 서명**은 “같은 장비·드라이버·자원 조건인가”를 확인한다.
GPU가 바뀌어도 논리적으로 같은 실험을 비교할 수 있지만, 과거 측정값을
다른 환경에서 측정한 값처럼 재사용할 수는 없다.

현재 공개 저장소에서 재현할 수 있는 데모는 **가상 결과를 명시한 API 검증
데모**다. 실제 GPU 벤치마크 결과라고 해석하면 안 된다.

```sh
uv sync --locked --extra pipelines
uv run pytest tests/test_api_flow.py -q -s
```

현재 완료한 범위는 실행 계약·API·저장·조회·검증·추천·승인과 실행 어댑터의
초기 구현이다. 실제 클러스터 연결 검증, 예산을 지키는 파일럿 실행, BO 탐색,
NPU 모델 실행, 통합 관리 화면은 후속 구현·검증이 남아 있다.
