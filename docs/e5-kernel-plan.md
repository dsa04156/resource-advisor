# E5 CUDA kernel versus input-supply diagnosis — frozen protocol v1

Publish this protocol and its source/tests before GPU execution. This is a
bounded functional acceptance experiment, not a powered performance-superiority
study. The previous eight-Job trial established serial wall-time hypotheses but
did not trace CUDA kernels. Do not relabel launch/synchronization wall time as
device utilization or declare the E5 compute scenario proved by it.

## Question and fixed workload

Can the existing phase diagnostic distinguish an input-supply-dominated case
from a CUDA-path-dominated case, with actual kernel activity to check the latter,
while retaining one GPU in both? Measure input reuse's effect and the additional
profiler distortion separately.

- Same deterministically initialized three-convolution 32-channel CNN as the
  original diagnostic recipe; generated input `[32,3,128,128]`, FP32, TF32 off,
  deterministic cuDNN, model/input seed 20261009. This new batch has a new identity.
- Twelve blocks; four forwards per block on the same logical preprocessed input.
  Three warmup forwards precede timing. Validate all 48 outputs against the CPU
  reference outside timing but inside Job cost, with atol/rtol 1e-4 and agreement
  1.0. Limit peak allocated framework memory to 2048 MiB. No classification claim.
- Fixed one physical GPU, one CPU, 2048 MiB host memory, same pinned qualified
  runtime/node and existing Kueue quota. No sharing, driver change or upgrade.
- `recompute`: run the same CPU average-pooling preparation for each forward.
  `cache`: reuse it, charging the first cache fill inside the objective.
  Both copy four tensors to the GPU and execute four identical forwards per block.
  No sleeps, global load generators, network faults or GPU resets induce a result.
- The three serial phases are CPU preparation, H2D transfer with synchronization,
  and forward with synchronization. NVML brackets are outside the objective and
  inside Job cost; preserve raw thermal/power readings and missing values.

## Assignment and replication

The Job is the experimental unit. Twelve blocks inside a Job are subsamples,
not independent replications. Three temporal blocks each contain all four arms:
`cache-plain`, `recompute-plain`, `cache-profiler`, `recompute-profiler`.

Use the frozen [schedule](evidence/e5-kernel-plan-v1.json), generated by seeded
permuted blocks (`numpy.random.default_rng(20261009)`, NumPy 2.2.6). The
experimental-design skill's `block_randomization` generated the layout before
measurement. Do not reorder it based on results. Three independent Jobs per
arm follow the existing minimum-repeat quality contract; they do not support
population tail estimates or a powered superiority test.

Two qualification Jobs precede the schedule: cache-plain runtime/output and
cache-profiler CUDA trace support. Stop if either fails; preserve its cost.
Maximum **14 GPU Jobs**, **1260 allocated GPU seconds**, **1800 seconds from
first qualification submission to the end of execution/collection**. Per Job
execution deadline is 90 seconds. Reserve that upper bound before each next
submission; never treat unknown allocation as zero. Queue waits remain separately
bounded. An observation timeout requires inspecting the same Job UID/attempt,
not another submission. No replacement run or automatic repeat-until-pass.

## Profiler separation and evidence

Six plain runs use the normal API/result/phase/thermal/artifact path. Six
profiler-on runs are explicitly diagnostic jobs under the same queue/quota,
with separate workload/context identity and no normal result envelope. Their
timings cannot enter normal execution profiles or drive recommendations.
Qualification and diagnostic allocations remain in the trial's separate cost
records; all 14 Jobs must be accounted for.

Use PyTorch 2.8 CPU/CUDA activities with shape/stack/memory profiling disabled.
Warmup finishes before profiling starts. Named forward ranges end only after
CUDA synchronization. Retain every captured CUDA kernel name, relative start
and duration within those ranges, tied to result/attempt identity. Reject a
CPU-only trace, missing block, nonfinite/negative time, overlapping serial
markers, unexpected GPU or kernel outside its owned range. Union overlapping
kernel intervals rather than double-counting concurrent streams.

Kernel interval union is device activity elapsed time, **not SM occupancy**,
peak-FLOP utilization or an arithmetic-versus-memory-bound diagnosis. Compare
profiler-on and profiler-off durations within each temporal block and arm,
retaining negative differences as measurement variation. Do not present traced
times as uninstrumented performance. PyTorch documents the relevant trace API
and overhead in its [2.8 profiler reference](https://docs.pytorch.org/docs/2.8/profiler.html).

## Fixed acceptance and analysis

Report quality/memory/thermal qualification separately from bottleneck outcomes.
An unexpected diagnosis is retained as a failed/unresolved E5 scenario, not a
reason to change thresholds, batch size or the schedule within this protocol.

1. Every plain Job must have the correct phase/result identity and quality/memory
   limits, unchanged GPU count, queue admission, one ledger/MLflow record and
   matching S3/API/MLflow artifacts. Profiler Jobs must not produce API profiles.
2. All three plain recompute runs should produce `POSSIBLE_INPUT_SUPPLY_BOUND`;
   all three cache runs should produce `POSSIBLE_ACCELERATOR_PATH_BOUND` under
   unchanged `serial-phases-v1`. Its 60%/80%-of-steps rules remain heuristics.
3. Every cache-profiler run should have real CUDA kernels in all twelve blocks
   and kernel interval union at least 60% of synchronized forward-marker duration.
   This supports a CUDA-kernel-dominated forward path, not SM saturation.
4. Report all raw per-Job/step/phase/kernel values, paired plain-run differences,
   group means/SDs, profiler paired overhead and full qualification/diagnostic/
   application costs. No p-values, outlier exclusion or selection of best runs.
5. Report whether any GPU reduction was proposed/applied (expected zero). Keep
   quality, original model/input hashes, platform records, unrelated workloads,
   Secret/PVC/static spec and queue quotas protected. Only append the new
   immutable runtime binding and reload the idle platform worker if needed.

This repeated-input fixture cannot justify caching changing real datasets.
Physical storage/network bottlenecks and broad data-loader concurrency are
separate questions. Unsupported Slurm hardware is not substituted with these
Kubernetes results, and overall completion still needs both specified backends.
