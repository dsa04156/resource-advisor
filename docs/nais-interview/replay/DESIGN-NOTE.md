# 오프라인 재생 화면 설계 메모

운영자가 저장된 요청 큐와 노드 배치를 한 관측 시점 기준으로 되짚어 보는 화면이다. live 콘솔이 아니며, 새 작업이나 실험을 실행하지 않는다.

- 구성: 상단 셸(제목·기록 재생 배지와 기록일·시나리오 선택·출처 패널) → 이 관측 기준 상태별 건수(누르면 필터)와 검색 → 작업 영역(전체 폭 실행 흐름 → 노드 배치 | 선택 요청 inspector → 요청 목록) → 하단에 고정된 타임라인(재생·탐색·속도, 이벤트 종류 눈금). 요청별 표는 중복이 크므로 기본으로 접고, 기본 `<details>` "요청 상세 목록"을 열어 본다. 단계 끝 요약(마지막 관측)은 접힌 표 밖에 보인다.
- 요청 큐, 노드 목록, inspector는 같은 관측(`state.index`)을 쓴다. 요청을 고르면 노드 목록에서 실제 배치 노드(실선 강조), 라우팅 대상(점선), 재시도 제외 노드(빨간 점선)가 강조된다. 노드를 누르면 표가 그 노드의 요청만 보이도록 걸러진다.
- 배치 판정: Pod 노드가 있거나, 상태가 ADMITTED/RUNNING/COLLECTING/FINALIZING/SUCCEEDED/FAILED이거나, 시작 시각이 기록된 경우에만 "실제 배치"로 본다. 그 전에 기록된 fleet `node`는 "대상"(라우팅 대상)이며, 장치 모델은 실제 배치 노드에만 붙인다.
- 색: navy 글자, 파랑 선택·실행, 호박색 대기, 청록 성공, 빨강 실패. 흰 패널과 옅은 중립 바탕, 얇은 테두리, 4px 간격. 그라데이션·대형 KPI 카드·장식용 nav는 쓰지 않는다.
- 노드 용량·사용률은 재생 데이터에 없으므로 표시하지 않고, 그렇다고 명시한다. Kueue admitted/pending은 별도 출처로 표기한다.
- Mobilint ARIES2(요청 11, NPU-B)는 2026-10-08 별도 기록으로, fleet 시나리오에서 항상 따로 표시하고 10건 합계에서는 빠진다. 종료 요약에서만 기존처럼 11건으로 센다.
- 1366×768에서는 한 화면 셸로 동작하고 작업 영역 하나가 세로 스크롤된다. 첫 화면에는 실행 흐름(대기 카드 약 200px, 3열)과 노드 배치 요약 윗부분이 보이고, 스크롤하면 노드 전체·inspector·요청 목록이 나온다(숨기지 않음). 노드 목록은 넓은 화면에서 격자로 놓인다. 1100px보다 좁으면 1열로 쌓이고, 390px에서는 흐름 단계가 세로로 쌓이며 표 행은 카드형이 된다. 하단 고정 타임라인은 문서 끝에 붙어 마지막 내용을 가리지 않고 기록 재생 태그를 보여 준다. 기본 컨트롤만 쓰며, reduced motion 설정에서는 행 강조 애니메이션을 끈다.
- 실행 흐름(작업 영역 맨 위, 전체 폭): 도착 전·접수 → 대기 큐 → 승인·실행 노드 → 결과. 단계는 그 관측 스냅샷의 상태 그대로이고, 파란 테두리와 `← 이전 단계` 표시는 직전 관측과의 차이만 뜻한다. 대기 큐는 관측 우선순위 높은 순 → 현재 시도 제출 시각 순으로 **표시**하며, 스케줄러의 실제 처리 순서라고 하지 않는다. 카드에는 요청 번호·우선순위·요청 GPU 수·기록된 대기 사유·제출 후 경과를 쓴다. 제출자는 기록에 없으므로 사용자 이름을 만들지 않는다.
- 정책 이벤트 줄(이 관측의 기록 변화): 상태 전이, 승격 이벤트 기록(10→100, aging 사유 원문), 스냅샷 우선순위 값 변경(이벤트 기록보다 늦게 반영될 수 있어 따로 표시), 승인·배치 노드, 2-worker barrier 해제, 실패 시도·재접수·제외 노드, Kueue admitted/pending 변화. 같은 구간의 변화일 뿐 원인 관계는 기록되지 않았다고 명시한다. KAI·backfill 등 데이터에 없는 정책은 표시하지 않는다.
- 선택은 흐름 카드·이벤트·표 행·노드 칩(실제 배치/대상 요청, w0/w1 rank 표시) 어디서든 같은 `state.selected`를 바꾼다. 노드 버튼은 필터, 칩은 요청 선택이다. 다시 그린 뒤에는 저장해 둔 포커스 요소의 식별자(row/card/chip/node/group)로 대체 요소에 포커스를 되돌리고, 걸러져 없으면 전체 필터·노드·요청 큐 제목으로 돌아간다.
- 다중 worker 그룹 시나리오(`gang-observations.json`, 별도 작업자가 저장 기록에서 추출)는 있을 때만 선택지로 보인다. Kueue workload 입장(Pod 2개 한 단위) + worker barrier 관측이며, 원자적 Pod 배치나 DDP가 아니라고 흐름 머리말에 쓴다. adaptive의 2-GPU 요청을 새 gang 증거로 표시하지 않는다.
- 원본은 `offline-demo.template.html`이다. `../offline-demo.html`은 `build_offline_demo.py`(그리고 이를 부르는 `build_visuals.py`)가 생성한다. `observations.json`은 기존과 같은 압축 JSON으로 `__OBSERVATIONS_JSON__`에, `gang-observations.json`은 별도 `__GANG_JSON__`에(없으면 `null`) 넣으므로 기본 payload 바이트는 바뀌지 않는다. fetch 없이 file://에서 열린다.
- 기본 시나리오 `N건 시뮬레이션 · 합성`(라벨의 건수는 데이터 `rows` 길이)은 `generate_simulation.py`가 고정 규칙으로 만든 **합성** 데이터 `simulation-observations.json`이며, `build_offline_demo.py`가 별도 `__SIM_JSON__` 슬롯(없으면 `null`, 선택지 숨김)에 넣는다. 실제 작업 제출·클러스터 호출·측정이 없고, 기존 기록 시나리오와 `observations.json`·`gang-observations.json`은 바꾸지 않는다. 가상 노드 `SIM-N1~N4`는 선언 용량(GPU 4/4/2/2)만 가지며 실습실 장비 이름·모델·측정 사용률을 쓰지 않는다. 규칙은 우선순위 → 가상 도착 순, 여유가 맞는 노드 중 가장 꽉 차는 노드, 2-GPU 그룹은 한 노드이고, 어떤 프레임도 용량을 넘지 않는다. 시각은 가상 시계(`가상 T+초`, 기준 2000-01-01은 실제 날짜가 아님)다. 첫 화면은 모든 요청이 도착한 뒤 실행·성공·대기가 동시에 많은 대표 프레임(`initial_index`)이고, 처음(|◀)부터 재생하면 도착 → 대기 → 실행 → 완료가 진행된다. 합성임을 상단 배지·모바일 고정 태그·흐름 머리말·변화 줄·출처 패널·노드 목록 꼬리말·inspector에 쓰고, 시뮬레이션에서는 Mobilint 별도 기록을 숨긴다. 검사: `test_simulation.py`, `browser_check_simulation.py`.
