1. 한 페이지 요약

Resource Advisor(RA)는 Kubernetes와 Slurm 위에 놓인 상위 control plane이다. 스케줄러를 새로 만들지 않고, 여러 클러스터의 GPU를 하나의 물리 풀로 합치지도 않는다.

질문 답
RA가 하는 일 공통 Job 계약, 프로젝트×클러스터 route, 제출 intent의 내구 기록(PostgreSQL outbox), 불확실 제출의 reconcile, 종료 상태와 usage 장부, 클러스터 인벤토리 관측
RA가 하지 않는 일 노드 bind와 admission(K8s는 Kueue가 admission, kube-scheduler가 bind, Slurm은 slurmctld가 결정. 단 현재 K8s 경로는 RA가 검증한 후보 노드를 kubernetes.io/hostname nodeSelector로 고정하므로 kube-scheduler가 노드를 자유롭게 고르지 않는다 — 5.2절), 전역 쿼터·공정성, 두 스케줄러의 같은 GPU 공동 소유, Slurm REST 연동
지금 실제로 돌고 있는 것 네임스페이스 resource-advisor-lab의 API, worker, Kubernetes 인벤토리 수집기, 가상 Slurm 인벤토리 수집기(모두 1/1, 08:09 UTC evidence-snapshot.json)
연결된 클러스터 lab-kubernetes 12 노드(Ready 10, 스냅샷 status partial) · virtual-slurm-140 6 노드, 가상 GPU 슬롯 8개(4/2/1/1) · lab-slurm 2 노드(2026-10-22 이후 stale, 이력만 보존)
가상 Slurm으로 가는 길 HTTP·REST가 아니라 SSH(22) forced-command → docker exec --user slurm slurmctld → scontrol/squeue JSON(v0.0.42)
가상 Slurm 실행 미검증. 실행 route는 예시 설정뿐이고 API에 등록되지 않았으며 worker manifest는 replicas: 0이다. sbatch는 한 번도 보내지 않았다
왜 이 구조인가 연구기관 GPU 운영에서는 K8s(서빙·컨테이너)와 Slurm(HPC 배치)이 공존한다. 각 스케줄러의 정책은 그대로 두고, 요청·상태·사용량을 한 장부로 설명할 수 있게 한다

면접에서 한 문장으로 말하면 다음과 같다. "기존 스케줄러가 배치를 결정하고, RA는 누가 무엇을 요청했고 어디서 어떻게 끝났는지를 잃어버리지 않게 기록하는 계층입니다. 가상 Slurm은 현재 관측까지 연결했고, 실행은 일부러 막아 두었습니다."

5.1 관측

InventoryCollector.collect (inventory.py)는 30초마다 kubectl로 세 가지를 읽는다.

  1. kubectl get nodes -o json — capacity/allocatable, Ready, nodeInfo
  2. kubectl get pods --all-namespaces -o json — 노드별 요청량(requests) 합 (사용률 아님, pod_request)
  3. kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes — metrics API

추가로 Kueue Workload/LocalQueue/ClusterQueue를 읽는다(queue_inventory.py). 권한은 inventory-rbac.yaml의 get/list뿐이다: nodes, pods, metrics nodes, clusterqueues(get), 네임스페이스 Role로 workloads, localqueues. 쓰기 권한은 없다.

장치 텔레메트리는 Prometheus 바인딩(MetricBinding: query + timestamp_query)으로 붙는다. 과거 live trial에서 DCGM GPU, Jetson GPU 사용률, Mobilint 사용률·메모리·온도를 읽은 기록이 있다(inventory.md "Actual lab evidence", inventory-live.json). 모든 값은 signal() 형식(value, observed_at, source, status, unit)으로 저장되고, 읽을 때 fresh_view가 시각을 다시 평가해 오래된 값은 null + stale로 바꾼다. 미측정은 0이 아니라 unknown이다.

장치 수 해석 주의: - 공유·time-slicing 단위(HAMi 공유 단위, nvidia.com/gpu.shared Jetson 슬롯)는 논리 슬롯이지 물리 장치 수가 아니다 (common-gpu-pool.md). - Jetson은 GPU와 CPU가 메모리를 공유(integrated memory)하므로 GPU 메모리를 독립 용량으로 더하지 않는다. - NPU(Mobilint, Hailo 등)는 별도 장치 클래스다. CUDA GPU 용량에 합치지 않는다.

5.2 Kueue admission과 kube-scheduler placement는 다른 단계다

단계 누가 무엇을 결정 RA가 보는 것
제출 RA worker kubectl create -f -로 Job 생성. 라벨 kueue.x-k8s.io/queue-name(LocalQueue), 선택적 kueue.x-k8s.io/priority-class KubernetesBackend.manifest/submit (backends.py)
admission Kueue [오픈소스] 이 Workload를 지금 들여보낼지만 결정. ClusterQueue 쿼터 안이면 쿼터를 예약하고 ResourceFlavor를 할당한 뒤 Job suspend 해제. 초과면 QuotaReserved=False로 대기(거절 아님). Pod를 어느 노드에 둘지는 정하지 않는다 KubernetesBackend.admission이 kueue.x-k8s.io/job-uid=<UID>로 Workload를 찾아 조건 기록
placement kube-scheduler [오픈소스] admission 이후 생성된 Pod를 제약(RA가 넣은 kubernetes.io/hostname·kubernetes.io/arch nodeSelector, flavor의 노드 조건, 요청량, taint 등) 안에서 bind. hostname이 고정돼 있으므로 사실상 그 한 노드에 bind할 수 있는지만 판단한다 KubernetesBackend.manifest가 검증된 후보의 node_ref를 hostname nodeSelector로 설정(spec.nodeName은 쓰지 않음). Pod의 노드·시각은 status로 관측
실행·종료 kubelet/컨테이너 런타임 실제 실행 status/result

현재 구현 vs 향후 설계: 지금 RA는 후보 노드를 직접 검증하고 hostname nodeSelector로 고정한다(backends.py KubernetesBackend.manifest). kube-scheduler는 그 제약 안에서 bind만 한다. "풀(pool) 조건만 주고 노드 선택은 kube-scheduler에 위임"하는 방식은 향후 설계이며 현재 구현이 아니다.

실제 Kueue 거동 기록: 1 GPU 쿼터에 2 GPU 요청 → Job 생성은 성공, QuotaReserved=False로 suspend 유지, Pod 없음(kueue-policy.md, 2026-10-02 [과거 기록]). Slurm도 한도 초과가 늘 거절은 아니다. 과거 별도 lab 기록에서 DenyOnLimit QOS 플래그와 AccountingStorageEnforce=associations,limits,qos를 켰을 때 job별 한도 초과(CPU·메모리·시간)와 미할당 QOS는 제출 거절됐지만, account 집계 한도(AssocGrpCpuLimit)는 대기였다(slurm-policy.md [과거 기록]; 현재 virtual-slurm-140은 AccountingStorageEnforce=none). RA는 native 사유로 대기(QUOTA_OR_LIMIT_PENDING: Kueue QuotaReserved=False, Slurm AssocGrp*/QOSGrp*/QOSMax*)와 거절(NATIVE_REJECTED)을 따로 분류한다(ARCHITECTURE.md Policy contract).

KAI Scheduler는 미검증이다. 이 저장소에 KAI 연동 코드나 실행 기록은 없다(CURRENT-STATE-AUDIT.md 4절 마지막 줄: "No scheduler algorithm, global quota, SlurmREST, OIDC, KAI…").

5.3 소유권 확인 (이름 재사용 대비)

Kubernetes Job 이름은 attempt ID다. 같은 이름이 삭제 후 재생성될 수 있으므로 KubernetesBackend.owns는 annotation resource-advisor/job-id, resource-advisor/context-signature가 일치하고, backend_uid가 이미 묶여 있으면 UID까지 일치해야 자기 Job으로 인정한다. UID는 제출 응답, 응답 손실 뒤 adopt, 또는 첫 관측(reconcile) 때 backend_uid로 저장되며, 그 전에는 annotation 일치로만 확인한 뒤 그 시점에 UID를 묶는다(KubernetesBackend.owns/reconcile, worker.py adopted_body). 취소도 DeleteOptions.preconditions.uid로 같은 UID만 지운다(RESULTS.md Review round 2).

6.2 관측 경로 [배포·관측]

  1. ra-virtual-slurm-140-inventory Pod가 30초마다 SlurmInventoryCollector.collect 실행 (slurm_inventory.py).
  2. read()가 ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=5 ra-virtual-slurm-140-observer '<명령>' 실행. 호스트 키는 Secret의 known_hosts에 고정.
  3. <SLURM_HOST>의 authorized_keys가 이 키를 restrict,from="<ADVISOR_EGRESS_IP>"와 forced command slurm_observer.py --config …로 묶는다. 클라이언트가 보낸 명령은 SSH_ORIGINAL_COMMAND로만 전달된다.
  4. observe() (slurm_observer.py)가 정확히 두 가지 명령만 허용한다.
  5. scontrol --json=v0.0.42 show nodes
  6. squeue --json=v0.0.42 --account=ra-lab --partition=all
  7. 허용되면 /usr/bin/docker exec --user slurm slurmctld /usr/bin/<cmd> …로 실행(환경 PATH=/usr/bin:/bin, 15 s timeout).
  8. 응답 검증: data_parser/v0.0.42, release 24.11.5, 8 MiB·10,000행 상한, 허가된 노드 6개가 정확히 있는지, 큐 행이 ra-lab/all 밖으로 새지 않는지. 허용 필드만 남겨(NODE_FIELDS, JOB_FIELDS) 반환.

9. 공통 Job 흐름 (개념도 — 가상 Slurm 제출은 비활성)

아래는 RA가 Kubernetes route와 기존 Slurm route에서 쓰는 흐름이다. 가상 140 route에서는 6단계의 원격 호출 전에 validate에서 막힌다.

단계 일어나는 일 코드 장애 시
1. 접수 POST /api/v1/compute/jobs + Idempotency-Key 헤더 api.submit → Service.submit (service.py) 같은 키+같은 body는 같은 job 재반환, 다른 body는 Conflict
2. intent 기록 한 트랜잭션에 VALIDATED job, attempt_id(a-…), outbox submit-<attempt> store.enqueue 커밋 전 실패면 아무것도 없음
3. lease route가 맞는 worker만 이벤트를 가져감 (FOR UPDATE SKIP LOCKED, lease token) store.claim(job_routes=…), store.job_route_filter lease 만료 시 다른 시도가 이어받음, stale finish는 token으로 차단
4. 사전 검증 호환성·승인·deadline·backend.validate Worker.submit_one 원격 호출 전 실패는 FAILED(PRE_SUBMISSION_*) — 가상 140은 여기서 멈춤
5. 제출 의도 커밋 SUBMITTING을 먼저 커밋 Worker.submit_one 이후 crash는 재제출이 아니라 reconcile 대상
6. native 호출 K8s: kubectl create; Slurm: sbatch --parsable(SSH forced-command) KubernetesBackend.submit, SlurmBackend.submit 응답 손실·timeout → SUBMISSION_UNKNOWN; 허용 목록에 있는 거절 문구만 FAILED(native_rejection)
7. native ID QUEUED + external_id(K8s Job 이름, Slurm job ID). K8s UID는 backend_uid에 따로 저장 native_name, SlurmBackend.external_id —
8. reconcile 불확실하면 attempt 이름으로 찾음. K8s: get job <attempt> + 소유권; Slurm: squeue --name/sacct --name … --duplicates Worker.reconcile_submission, *.reconcile MATCHED 채택 / NO_MATCH·AMBIGUOUS·QUERY_FAILED는 열린 상태 유지
9. 상태 추적 RUNNING, Kueue 조건, Slurm %r 대기 사유 Worker.reconcile_all, status, admission 조회 실패는 unknown이지 부재가 아님
10. 결과 결과 envelope 수집(K8s 로그, Slurm results 키의 bounded tail) → 검증 result, result_from_log 형식 불일치 → RESULT_INVALID
11. 종료+usage 종료 상태와 ra_usage 1행을 같은 트랜잭션에 기록, attempt가 PK store.change_job → record_usage, accounting.py ledger_record 재실행·backfill은 새 행을 만들지 않음
12. 게시 아티팩트·MLflow 전달(outbox) MLflowDelivery (worker.py), artifacts.py 전달 실패는 재시도, 결과 상태와 분리

조회: GET /jobs/{id}, GET /jobs/{id}/lifecycle(reconcile 이력 최근 10개, 연속 no-match 수), GET /usage/report?month=YYYY-MM. 운영자는 POST /jobs/{id}/submission-resolution(ACKNOWLEDGE_UNRESOLVED)로 감사 기록만 남긴다. 이 조치는 job을 종료시키거나 usage를 쓰지 않고, 늦게 나타난 native job은 여전히 채택된다(ARCHITECTURE.md Lifecycle contract).

현재 미해결: 2026-10-28 live-k8s-cpu의 SUBMISSION_UNKNOWN 2건이 열려 있다. acknowledge하지 않았고 테스트 job으로 재사용하지도 않았다(deployment-20261029.json pre_existing_unresolved). 따라서 "zero-loss가 증명됐다"고 말하지 않는다. 말할 수 있는 것은 "불확실한 제출을 성공이나 실패로 둔갑시키지 않고 열어 둔다"는 설계다.

11.1 쿼터는 native가 소유한다

RA route 값 Kubernetes Slurm(가상 140)
큐 local_queue → Kueue LocalQueue → ClusterQueue 쿼터 partition: all
회계 단위 (네임스페이스/큐) account: ra-lab

route drift 방지: 계획(scheduling_plan)이 저장된 job은 실제 어댑터 값이 다르면 verify_adapter_plan이 SCHEDULING_BINDING_DRIFT로 제출 전에 거부한다(scheduling.py). RA는 전역 쿼터를 추가하지 않는다.

11.2 usage 단위

  • 기록 대상은 native evidence로 관측된 예약량이다: K8s는 스케줄된 컨테이너 requests + Pod 시각, Slurm은 sacct AllocTRES + 시작/종료 시각. 요청량도 사용률도 아니다.
  • allocation_mode(physical_device, virtual_slot, cpu_only), 장치 클래스, 모델, 클러스터, 자원 키는 합치지 않는다. 환율을 만들지 않는다.
  • 가상 140의 gres/gpu 시간은 virtual-slot 시간이다. gres/gpumem, gres/gpuutil은 Slurm이 자동 등록했지만 JobAcctGatherType이 없어 측정되지 않는다 → unknown.
  • /usage/report는 [start, end) UTC로 구간을 자르고, 끝나지 않은 attempt는 not_finalized로 따로 나열한다(accounting.py period_report).

11.3 비트랜잭션 외부 작업, TOCTOU, 멱등성

  • 외부 작업은 트랜잭션 밖이다. DB 커밋과 sbatch/kubectl create를 원자적으로 묶을 수 없다. 그래서 "의도 먼저 커밋 → 호출 → 결과 기록" 순서와 reconcile로 보완한다.
  • TOCTOU: 인벤토리에서 "비어 있다"고 본 순간과 native 스케줄러가 배정하는 순간 사이에 상태가 바뀐다. 인벤토리는 배치 권한이 아니다(execution_qualification: "inventory never grants runtime qualification or admission"). 최종 판단은 Kueue/slurmctld가 한다.
  • 멱등성: API는 (project, Idempotency-Key), 제출은 attempt 이름, usage는 attempt PK. 단, Slurm 쪽 이름 검색은 SlurmDBD가 있어야 응답 손실을 안전하게 복구할 수 있다(SlurmBackend.reconcile 주석). 가상 140에 SlurmDBD를 붙인 이유 중 하나다.
  • 동시성: CAS·lease·SKIP LOCKED는 테스트로 확인했지만 운영 자격은 route당 worker 1 replica(Recreate)다. HA 주장이 아니다.

16. 면접 예상 질문 12개

  1. RA가 스케줄러인가요? 범용 스케줄러는 아닙니다. Kubernetes에서는 Kueue가 admission(들여보낼지)을, kube-scheduler가 bind를 하고, Slurm에서는 slurmctld가 정합니다. 다만 현재 K8s 경로는 RA가 검증한 후보 노드를 hostname nodeSelector로 고정하므로 kube-scheduler는 그 제약 안에서 bind만 합니다. 노드 선택을 kube-scheduler에 맡기는 풀 단위 위임은 향후 설계입니다. RA는 요청·상태·사용량을 잃지 않게 하는 상위 control plane입니다.
  2. K8s와 Slurm GPU를 하나의 풀로 합쳤나요? 아닙니다. 한 GPU를 두 스케줄러가 같이 소유하지 않고, 장부와 화면에서만 나란히 보여 줍니다. 장치 클래스·할당 방식도 합산하지 않습니다.
  3. Slurm에 왜 REST가 아니라 SSH인가요? 이 환경에 slurmrestd가 없고, forced-command로 허용 명령을 코드 수준에서 제한하는 편이 범위를 좁히기 쉬웠습니다. 16817 포트가 열려 있어도 쓰지 않습니다. REST 전환은 범위 밖입니다.
  4. 가상 Slurm에서 작업이 돌았나요? 아닙니다. 관측과 accounting까지 확인했습니다. 실행 route는 예시 설정이고 worker는 0 replica이며 sbatch는 0건입니다. 전용 job UID와 적격 runtime이 생기기 전에는 실행하지 않습니다.
  5. 가상 GPU 8개는 무엇인가요? Slurm GRES에 등록된 슬롯입니다. 장치는 /dev/null 매핑이라 성능 의미가 없고, RA는 virtual_slot으로 분류합니다.
  6. 응답이 사라지면 중복 제출되나요? 원격 호출 전에 SUBMITTING을 커밋하고, 불확실하면 attempt 이름으로 reconcile합니다. 재제출하지 않습니다. 다만 미해결 2건이 남아 있어 zero-loss를 증명했다고는 말하지 않습니다.
  7. Kueue 쿼터 초과와 Slurm 거절의 차이는? Kueue는 Job을 만들고 admission을 보류합니다. Slurm은 정책에 따라 다릅니다. 과거 lab에서 DenyOnLimit+enforcement를 켰을 때 job별 한도 초과는 제출 거절, account 집계 한도는 대기였습니다. RA는 native 사유로 대기와 거절을 나누고, 거절은 허용 목록 문구일 때만 분류합니다.
  8. 사용량은 실제 사용률인가요? 아닙니다. native가 기록한 예약량(K8s requests+시각, Slurm AllocTRES+시각)입니다. 모르는 구간은 0이 아닌 unknown으로 남깁니다.
  9. 보안 경계는 충분한가요? 명령 화이트리스트·키 분리·출발지 제한·host key 고정은 실측으로 거부를 확인했습니다. 하지만 gateway 소유 계정이 docker 그룹이라 root 격리는 아닙니다.
  10. status가 partial인데 장애인가요? 아닙니다. 노드·큐 관측은 ok이고 Prometheus 메트릭이 연결되지 않았다는 뜻입니다.
  11. ClusterID 사건은 무엇이었나요? accounting 전환 때 ID 불일치로 약 90초 컨트롤러 재시작 루프가 있었고 즉시 롤백했습니다. 큐는 비어 있었고 job counter와 백업은 보존됐습니다. 원인을 소스에서 확인한 뒤 identity 파일만 옮겨 다시 적용했습니다.
  12. 다음 단계는? 전용 비특권 job UID, 적격 runtime 바인딩, 그다음 2분 이하 smoke 1건과 응답 손실 복구 시험입니다. 그 전에는 데모 범위를 관측으로 한정합니다.

2. 50–60초 압축 스크립트

Resource Advisor는 Kubernetes와 Slurm을 대체하지 않는 상위 control plane입니다. 쿠버네티스에서는 Kueue가 들여보낼지를, kube-scheduler가 노드를 정하고, Slurm은 slurmctld가 정합니다. 저희는 공통 Job 계약, 프로젝트별 route, PostgreSQL에 남기는 제출 intent와 사용량 장부, 그리고 응답이 사라졌을 때의 reconcile을 맡습니다.

지금 lab에는 API, worker, 쿠버네티스 수집기, 가상 Slurm 수집기가 떠 있습니다. 쿠버네티스는 읽기 권한으로 노드와 Pod 요청량, Kueue 큐를 30초마다 봅니다. 가상 Slurm은 Docker로 만든 6노드 클러스터인데, REST가 아니라 SSH forced-command로 들어가 허용된 JSON 조회 두 개만 실행합니다. GPU 8개는 가상 슬롯이라 성능 의미는 없습니다.

가상 Slurm 실행은 아직 열지 않았습니다. 전용 job 계정과 검증된 런타임이 없어서 worker를 0으로 두었고, 제출은 0건입니다. 다음 단계는 그 두 가지를 갖춘 뒤 짧은 smoke 한 건과 응답 손실 복구 시험입니다.

인증 Bearer 해시 비교. 현재 데모는 anonymous ra-lab 모드라 헤더 없는 요청도 ra-lab 비운영자로 허용, 운영자 API는 별도
왜 SSH냐 slurmrestd 없음, forced-command로 명령을 좁힘
GPU 8개 가상 슬롯, /dev/null 매핑
중복 제출 intent 선커밋 + attempt 이름 reconcile, 재제출 안 함. 미해결 2건 있음
쿼터 native 소유. Kueue는 대기. Slurm은 정책 따라 다름(과거 DenyOnLimit+enforcement에서 job별 초과만 거절, 집계 한도는 대기)
사용량 예약량이지 사용률 아님, unknown은 unknown
보안 명령 경계. docker 그룹 계정이라 root 격리 아님
partial 메트릭 미연결, 장애 아님
사건 ClusterID 불일치 ~90초, 롤백, 큐 비어 있었음
