# 공동 컴퓨팅 자원 운영 연습

이 화면의 목적은 연구자가 제출한 작업을 운영자가 확인하고, 자원·대기·실패·
사용량을 설명할 수 있게 하는 것입니다. Notebook은 연구 코드를 작성하는 도구,
Kubeflow는 워크플로 실행 도구이며, 운영 화면은 실제 백엔드와 기록을 조회합니다.
화면에서 직접 제출한 작업이 자동으로 Kubeflow Pipeline이 되지는 않습니다.

## 한 번 직접 해볼 순서

1. **운영 현황**에서 현재 프로젝트의 진행 중 작업과 장비 확인 항목을 봅니다.
   관측 실패는 장비 장애와 다릅니다. 오래된 관측이면 수집 상태부터 확인합니다.
2. **자원 현황**에서 사용할 GPU/NPU, CPU·메모리를 확인합니다. 물리 사용률과
   스케줄러 예약량을 구분하고, 미측정 값을 0%로 해석하지 않습니다.
3. **작업 제출**에서 등록된 실행 환경으로 템플릿을 만들고, 자원·우선순위·시간
   제한을 확인한 뒤 명시적으로 제출합니다. 저장만으로 실행되지는 않습니다.
4. **운영 현황 → 상세 · 조치**에서 상태와 대기 사유를 확인합니다.
   `Resources`는 자원 확보 대기, `Priority`는 우선순위 대기입니다.
   `AdmissionPending`만으로 쿼터 초과라고 판단하지 말고 **큐 · 쿼터**에서
   승인 조건을 확인합니다. `ImagePullBackOff`는 이미지 접근·연결을 확인합니다.
5. 취소가 필요하면 작업을 취소하고, 백엔드 종료가 확인되는지 봅니다.
   제출 결과가 불명확한 작업은 먼저 기존 제출 여부를 확인합니다.
6. **프로젝트 사용량**에서 종료 작업의 예약 장치 시간을 확인하고 CSV를 받습니다.
   실제 모델 실행 시간, 전체 예약 시간, 큐 대기 시간을 구분해 설명합니다.

운영 첫 화면의 경과 시간은 접수 이후 시간입니다. 큐 대기 시간은 종료 장부의
관측된 시간만 사용하며, 기록이 없으면 미확인으로 남습니다. 큐 카드의 범위도
다릅니다. Kueue ClusterQueue는 해당 큐 전체, Slurm은 설정된 계정·파티션입니다.

## 직무와 연결되는 경험

| 운영 업무 | 여기서 해볼 일 | 남길 근거 |
|---|---|---|
| 이기종 자원 관리 | GPU/NPU 등록·관측·실행 가능 여부 구분 | 자원 화면, 검증 기록 |
| 배치 작업 운영 | Kubernetes/Slurm 작업 제출·대기 사유 확인·취소 | 작업 ID, 백엔드 ID, 상태 시각 |
| 할당량·우선순위 | 큐 정책과 작업 요청 비교 | 큐 관측, 요청 우선순위 |
| 장애 대응 | 이미지 오류·노드 연결·메모리 부족 기록 확인 | 관측 오류 코드, 수행한 조치 |
| 사용량 보고 | 프로젝트 예약 시간과 미측정 구간 구분 | CSV와 개별 작업 장부 |

현재는 접속한 프로젝트 범위의 운영 화면입니다. 조직 전체 관리, 사용자별 과금,
웹에서의 큐 정책 변경, 자동 장애 복구를 구현한 것으로 설명하면 안 됩니다.
장비 설치·드라이버 검증·복구·접근 통제는 별도 실습과 실행 근거가 필요합니다.
이번 화면 변경만으로 새 하드웨어 실행이나 장애 복구 실험이 완료되지는 않습니다.
