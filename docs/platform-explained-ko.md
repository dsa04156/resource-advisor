# 이 플랫폼은 무엇을 직접 만들었나

연구자가 작업과 필요한 조건을 제출하면, 검증된 실행환경을 찾고 실제 큐에
넣어 실행한 뒤 결과·실험 기록·사용량을 연결하는 플랫폼이다. 이후에는 같은
조건에서 모은 실측 결과로 다음 실행 설정을 추천하고, 승인 후 별도로 확인한다.
전체 HAIRP의 완성은 아직 아니다. 이 문서는 현재 실제로 동작한 범위를 설명한다.

## 구성요소를 분리한 이유

| 구성요소 | 쉬운 설명 | 여기서 맡기는 일 |
|---|---|---|
| Notebook | 연구자가 코드를 작성하고 셀별로 실행하는 작업 공간 | 작업 정의와 API 사용. Notebook을 켰다는 사실만으로 GPU가 할당되지는 않는다 |
| Kubeflow Pipelines | 여러 실험 단계를 순서대로 실행하는 도구 | API launcher 실행과 workflow 상태 관리. 실제 GPU 작업과 pipeline 실행 ID는 별개 |
| Kueue | Kubernetes 작업의 입장 대기열 | 프로젝트 쿼터와 우선순위에 따라 실행 허용. Pod의 노드 배치는 Kubernetes가 수행 |
| Kubernetes / KubeEdge | 컨테이너를 노드에서 실행하는 기반 | 서버·Edge 노드 실행과 상태 관리 |
| Slurm | 별도 HPC 작업 큐와 실행 관리자 | Account/QOS/Partition과 실제 sbatch 작업. Kueue와 하나의 스케줄러로 합치지 않음 |
| MLflow | 실험 기록장 | 설정·측정값·파일과 run 상태 저장 |
| PostgreSQL | 플랫폼의 작업·정책·결과·비용 장부 | 제출과 실행을 식별하고 재시도·권한·사용량을 일관되게 관리 |
| Prometheus / exporter | 장비 상태를 측정하고 저장하는 기반 | CPU·메모리·GPU 등 실제 관측. 지원하지 않는 NPU 지표는 추정값으로 채우지 않음 |
| 운영 콘솔 | 연구자와 운영자가 보는 화면 | 대기 이유·할당·실행·결과·현재 자원·실험 당시 노드 상태 확인과 기록 재생 |

이 도구들은 서로 다른 문제를 해결한다. MLflow가 큐를 관리하거나 Kubeflow가
장치별 모델 호환성을 판단하게 만들지 않았다. 한 시스템을 재시작했을 때도
원래 작업 ID와 결과를 찾아 연결할 수 있도록 플랫폼이 관계를 저장한다.

## 기존 도구 위에 직접 추가한 다섯 가지

1. **공통 SchedulingProfile.** 연구자가 GPU 이름부터 고르는 대신 작업과
   자원 조건·정책을 제출한다. Kubernetes의 Queue/Flavor/Priority와 Slurm의
   Account/QOS/Partition으로 각각 변환하고 실제 설정과 맞는지 검사한다.
2. **실행환경 검증.** 자원이 등록돼 있어도 모델이 실행 가능한지는 별도다.
   코드·이미지·아키텍처·런타임·변환 모델·입력을 묶어 확인한다.
   [다른 Hailo 모델 파일을 넣은 실제 시험](hailo-artifact.md)에서는 실행 결과를
   만들기 전에 차단했다. CUDA 프로그램을 NPU에 자동 변환하는 기능은 아니다.
3. **근거 있는 추천과 승인.** 처음 보는 작업의 성능을 지어내지 않는다.
   비교 가능한 실측 이력이 없으면 관측하거나 추천을 보류한다. 동의와 예산
   안에서 후보를 시험하고, 추천 근거를 고정한 뒤 승인·독립 확인을 수행한다.
4. **실행과 기록의 일관성.** API Job, Attempt, 실제 scheduler Job, MLflow run,
   결과 파일과 사용량을 연결한다. 응답이 유실됐다고 GPU 작업을 다시 만들지
   않으며 취소·실패의 예약 비용도 남긴다.
5. **운영 과정의 시각화.** 대기 → 할당 → 실행 → 완료를 실제 상태로 보여준다.
   당시 노드 관측과 현재 상태를 구분한다. 기록 재생 애니메이션은 새 작업을
   실행하는 기능과 별개이며 과거에 없던 관측을 만들어 넣지 않는다.

예를 들어 같은 NPU 요청을 제출해도, 입장 여부는 Kueue가 판단하고 변환 모델의
정합성은 우리 runner가 검사한다. 결과가 통과하면 플랫폼이 실험 기록과 장부를
연결한다. 이 책임 구분과 실제 실패 복구가 개발한 부분이다.

## 차별점을 설명할 때의 정확한 표현

“Kubernetes/Kueue와 Slurm의 정책을 공통 API로 연결하고, GPU·NPU의 모델별
실행 가능성 검증과 실측 추천·승인·결과·사용량을 통합했습니다. 실제 장비에서
큐와 우선순위, 중복 제출 방지, 취소와 복구를 확인하고 운영 화면에 연결했습니다.”

백필·갱 스케줄링 자체를 새로 발명한 것은 아니다. 기존 scheduler 기능을
정책에 연결하고 실제 동작을 관측하는 부분을 구현했다. 기존 제품에 유사한
기능이 없다는 주장이나 자동 최적 배치·성능 향상 주장은 별도 근거가 필요하다.
현재 비교 실험은 추천 비용까지 포함하면 순이익이나 BO의 우월성을 증명하지 못했다.

## 최초 설계의 완료 상태

[최초 HAIRP 항목별 대조표](hairp-original-scope-ko.md)와
[독립 v0.3 수용시험 표](scenario-acceptance.md)를 별도로 유지한다.
현재 실제 GPU/NPU/Slurm/KFP 실행 경로가 있어도 두 설계의 전체 완료는 아니다.

- Slurm의 마지막 기존 작업은 관리 서버 연결 장애로 종료·비용을 확인하지 못했다.
  같은 작업을 재조회하며, 취소 요청을 취소 완료로 표시하지 않는다.
- Pi의 DEEPX는 PCIe 장치 탐지가 확인되지 않았다. 다른 Hailo 성공을 이 장치의
  성공으로 취급하지 않는다.
- 최초 HAIRP의 기존 stage 런타임 연결, Placement Engine v2의 실제 재배치,
  HAMi 간섭 비교, eBPF 연동과 네 종류 전체 pipeline 등은 추가 구현·연결이 남았다.

완료 여부는 설치 목록이나 화면의 수가 아니라, 각 요구 기능의 실제 실행과
검증 근거로 판단한다. 자세한 구현·실험 링크는 [차별점 문서](differentiation-ko.md)에 있다.
